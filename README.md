# CacheView backed by HybridCache validation sample

Sample for [aspnetcore issue 69126](https://github.com/dotnet/aspnetcore/issues/69126). It targets .NET SDK `11.0.100-rc.1.26425.128`, pinned in `global.json`.

## Purpose

The home page is a static SSR `CacheView`. Its child creates a Guid in `OnInitialized` and logs that initialization. The response also identifies the server outside the cached section. Two processes use Redis as `HybridCache` secondary storage, so the same cached markup can be observed across their separate local caches. `CacheView` selects the registered `HybridCache` automatically; `CacheViewHybridCache` is only necessary to select a particular instance. This means merely registering `HybridCache` changes where CacheView render output is cached.

The separate `/sliding` page intentionally uses `ExpiresSliding`. It must throw `NotSupportedException`; the public docs describe this limitation and advise `ExpiresAfter` or `ExpiresOn`. `/absolute-expiration` has the same cached child, cache key, and ten-second lifetime, using `ExpiresAfter` instead of `ExpiresSliding`.

## Documentation evidence

Checked 2026-09-21 against [ASP.NET Core Blazor CacheView component](https://learn.microsoft.com/en-us/aspnet/core/blazor/state-management/cacheview-component?view=aspnetcore-11.0), **Expiration and cache storage**: "If a `HybridCache` service is registered, `CacheView` uses it automatically. `RazorComponentsServiceOptions.CacheViewHybridCache` can select a specific `HybridCache` instance instead. Sliding expiration isn't supported with `HybridCache`; use `ExpiresAfter` or `ExpiresOn`."

This directly answers both documentation questions: registration changes the store selected for `CacheView` output, and the sliding-expiration limitation is documented, not only enforced at runtime.

## Prerequisites and setup

1. Confirm the pinned SDK is available: `dotnet --list-sdks`. This machine has the required .NET 11 RC1 SDK and ASP.NET Core runtime.
2. Install Docker Desktop or provide a reachable Redis server. Docker is not installed on this machine. The WebAssembly and MAUI workloads are also absent: `dotnet workload install wasm-tools` and `dotnet workload install maui` are required for those configurations.
3. Choose a Redis/proxy setup. With Docker Desktop, run `docker compose up -d redis proxy` at the repository root. Without Docker, start a reachable Redis server and a locally installed Caddy/IIS/nginx proxy that round-robins to ports 5101 and 5102 without sticky sessions.
4. Restore and build with `dotnet restore` then `dotnet build`. Do not use `dotnet run` until ready to perform the manual checks.
5. In terminal A start instance A: `dotnet run --project .\HybridCacheValidation --urls http://localhost:5101 -- --Validation:InstanceName=Instance-A`.
6. In terminal B start instance B: `dotnet run --project .\HybridCacheValidation --urls http://localhost:5102 -- --Validation:InstanceName=Instance-B`.
7. Browse through the proxy at `http://localhost:8080/?entry=shared-01`. Preserve console logs from both terminals at Debug level. Record the proxy URL in every proxy-scenario evidence capture; direct `5101`/`5102` captures do not demonstrate proxy routing.

The connection string is in `HybridCacheValidation/appsettings.json`. For another Redis host, override `ConnectionStrings__RedisConnectionString`. The `abortConnect=false` setting keeps the application alive while Redis is unavailable, which makes outage and recovery observations possible.

Before every testcase, open both instance terminals side by side. Clear the terminal display or place a visible separator line in each terminal, then use a new `entry` value specified by the testcase. In the browser, use an InPrivate window or DevTools Network with **Disable cache** selected. A `CachedGuid initialized` log line means the child rendered; no such line on a request is evidence that cached markup was replayed.

## TC-12: In-memory sliding-expiration control

The same `/sliding` component was run without registering `HybridCache` using `dotnet run --project .\HybridCacheValidation --urls http://localhost:5103 -- --Validation:UseHybridCache=false --Validation:InstanceName=InMemory-Control`. It rendered successfully with the default in-memory `CacheView` store. Guid `01288093-03a6-4af0-9365-f2e4cffc787e` was reused on a reload within the ten-second sliding window. After more than ten seconds idle, it expired and a new Guid, `a20e3675-f6dd-49ff-899b-603fe402ea3e`, rendered. The server log contains exactly two `CachedGuid initialized` events across the three requests.

Evidence: `Evidence/TC-12/TC-12-01-in-memory-first-response.png`, `Evidence/TC-12/TC-12-02-in-memory-within-window.png`, `Evidence/TC-12/TC-12-03-in-memory-after-idle-expiry.png`, and `Evidence/TC-12/TC-12-04-in-memory-sliding-terminal.txt`. This passes the expected configuration contrast with TC-04: sliding expiration works with the default in-memory store and throws only when `HybridCache` is registered.

The same-page absolute alternative was also verified with HybridCache at `http://localhost:5101/absolute-expiration`. It uses the same `CacheView` key, child component, and ten-second lifetime as `/sliding`, with `ExpiresAfter` in place of `ExpiresSliding`. Guid `0087b325-f6e9-48c2-bad4-d8bc78d77344` was reused before expiry, then Guid `2dc0e62f-7c5a-4b91-99dd-a83f657ea12d` rendered after expiry. Evidence is in `Evidence/TC-05/TC-05A-01-absolute-counterpart-initial.png`, `TC-05A-02-absolute-counterpart-before-expiry.png`, `TC-05A-03-absolute-counterpart-after-expiry.png`, and `TC-05A-04-absolute-counterpart-terminal.txt`.

## Configuration coverage and also exercise

Use the same server app with Static SSR (no `@rendermode`) and Interactive Server. For Interactive WebAssembly and Auto, move only a non-cached diagnostic page into the Client project; `CacheView` itself caches static SSR GET output, so report that the sharing scenario is not applicable to client-only rendering. For Auto, test a storage-cleared first visit and a reload after WebAssembly resources cache. Standalone WebAssembly cannot test static SSR CacheView sharing; document it as configuration-not-applicable. MAUI is a separate app and requires the MAUI workload; report whether the API/setup is supported there rather than claiming two-server sharing.

Also exercise: publish (`dotnet publish -c Release`), upgrade a .NET 10 copy to the pinned SDK, WebAssembly trimming/AOT (`wasm-tools`), this non-sticky proxy/multiple-instance setup, Hot Reload (`dotnet watch` and edit the variant word), IDE and CLI builds, and containers. For the container run, install Docker Desktop and execute `docker compose -f docker-compose.container.yml up --build`; it creates Redis, original app A, changed app B, and a round-robin Caddy proxy at `http://localhost:8080`. Keep results per configuration and label anything skipped as `Not covered`.
